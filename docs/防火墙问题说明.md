# KHDownloader —— 防火墙（网络拦截）问题说明

> 本文只说明问题本身：它是什么、在哪一层、怎么被观测到、边界在哪、哪些还没弄清。
> 数据来自项目内的诊断记录与源码，采集日期 2026-10-11。

---

## 0. 先界定："防火墙"在这里指哪一件事

"防火墙"这个词套在这个项目上，其实混着两件完全不同的事，先把它们分开：

| | A. 站点侧的 Web 应用防火墙（**本项目真正遇到的问题**） | B. 本机 Windows 防火墙 / 系统代理 / 安全软件 |
|---|---|---|
| 是什么 | 站点把 `downloads.khinsider.com` 放在 Cloudflare 后面，对**程序化访问**下发人机校验 | 操作系统层面对进程进出网络的管控 |
| 出现在链路哪一段 | 服务器那一端 | 用户本机 |
| 项目里的表现 | 请求专辑页返回 `403` + `cf-mitigated: challenge` | **无表现** |
| 项目是否涉及 | 是，这是 v007 起诊断的核心 | **从未涉及** |

**第 B 类与本项目无关**：项目不注册防火墙规则、不改端口、不动出站/入站策略、
不修改系统代理或安全软件设置，代码里也没有任何相关调用。诊断记录里明确记着
"未修改系统代理 / 防火墙 / 安全软件"。所以如果遇到"是不是这软件动了我电脑的防火墙"，
答案是不涉及。

**下面讲的全部是 A 类**，也就是 `khdownloader_core.py` 里注释写的：
站点对程序化访问启用了 Cloudflare 人机校验，导致"输入专辑 URL 自动下载"这条路径
在部分网络出口下被挡在门外。

---

## 1. 问题的一句话描述

程序直接请求 KHInsider 的**专辑页**时，站点的 Cloudflare 防护返回
**HTTP 403 附带 `cf-mitigated: challenge`**，页面内容是一个 "Just a moment..."
的人机校验页 —— 普通 HTTP 客户端（不带浏览器执行环境）拿不到真正的专辑页内容，
因此**解析不出曲目列表**。

关键点：这**不是**"网站坏了"、也**不是**"没找到曲目"，
而是**请求在到站门口就被拦下来了**，压根没走到内容解析那一步。

---

## 2. 实测现象与原始证据

测试对象（固定案例）：

```
https://downloads.khinsider.com/game-soundtracks/album/
cross-channel-in-memory-of-all-people-special-soundtrack-2011
```

执行环境：Windows 10 (10.0.19045) / 64 位 / Python 3.11.9 / requests 2.34.2
执行环境的网络出口：`CF-RAY` 后缀 `-HKG`（Cloudflare 中国香港节点）

### 2.1 专辑页 —— 第 1 次请求

| 项 | 值 |
|---|---|
| 状态码 | **403** |
| 耗时 | 1.257 s |
| `Cf-Mitigated` | **`challenge`** ← 关键信号 |
| `Server` | `cloudflare` |
| `CF-RAY` | `a487b249782409d4-HKG` |
| 页面长度 | 6,092 字节 |
| 含 `<title>Just a moment...` | **是** |
| 含 `challenges.cloudflare.com` | **是** |
| 含 `table#songlist`（专辑页的曲目表） | **否** |

判定：真实的人机校验。两个**互相独立**的信号同时命中 —— 响应头 `cf-mitigated: challenge`
与页面特征（`Just a moment...` / `challenges.cloudflare.com`）。

### 2.2 专辑页 —— 第 2 次请求（换成完整浏览器请求头）

用真实 Chrome UA + `Accept` / `Accept-Language: ja,en-US` / `Sec-Fetch-*` 等完整头再请求一次：

| 项 | 值 |
|---|---|
| 状态码 | **403**（与首次一致） |
| 耗时 | 0.735 s |
| `Cf-Mitigated` | **`challenge`** |
| `CF-RAY` | `a48dea6cdce2b21b-HKG` |

**结论：与请求头 / UA 无关，从该出口出发是持续性的（2/2）。**
这排除了"换个 User-Agent 就能过去"这类情况。（仅据 2 次请求，未做高频重试。）

### 2.3 曲目页 —— 同一主机、不同路径

专辑页里每首歌的链接形如 `/game-soundtracks/album/<slug>/01%2520….mp3`，
**指向同一个被挑战的主机**。但实测该路径返回的是**曲目详情页**，且**未被挑战**：

| 项 | 值 |
|---|---|
| 状态码 | **200** |
| `Content-Type` | `text/html; charset=UTF-8` |
| HTML 长度 | 14,655 字节 |
| `<title>` | `群青のティファレス(GAME Size) MP3 - CROSS†CHANNEL … SPECIAL SOUNDTRACK` |
| 含 `Just a moment` / `challenges.cloudflare.com` | **否** |
| 含真实音频直链 | **是** → `lambda.vgmtreasurechest.com/…/01%20群青のティファレス(GAME Size).mp3` |

### 2.4 MP3 二进制 —— 换到了另一个子域

| 项 | 值 |
|---|---|
| 主机 | `lambda.vgmtreasurechest.com`（另一子域，不是 `downloads.khinsider.com`） |
| 状态码 | **200** |
| `Content-Type` | **`audio/mpeg`** |
| `Content-Length` | **4,930,262** 字节 |
| 前 16 字节 | `b'ID3\x04\x00\x00\x00…'` → 真 MP3 |
| `Cf-Mitigated` | 无 |

### 2.5 汇总

| # | 层级 | 主机 | 路径形态 | 状态码 | 关键头 | 判定 |
|---|---|---|---|---|---|---|
| 1 | **专辑页** HTML | `downloads.khinsider.com` | `/game-soundtracks/album/<slug>` | **403** | `Cf-Mitigated: challenge` | **被挑战（唯一阻塞点）** |
| 2 | **曲目页** HTML | `downloads.khinsider.com` | `/game-soundtracks/album/<slug>/NN…mp3` | **200** | 无 `cf-mitigated` | 未被挑战 |
| 3 | **MP3** 二进制 | `lambda.vgmtreasurechest.com` | `/soundtracks/<slug>/<hash>/NN….mp3` | **200** | `Content-Type: audio/mpeg` | 未被挑战 |

---

## 3. 分层定位：被挡的只有一层

这是整个问题里最要紧的结构性事实 —— **阻塞不是全链路的，而是集中在一个点上**：

```
[专辑页 HTML]  downloads.khinsider.com/album/<slug>          → 403 challenge   ← 唯一阻塞点
      │
      │   程序直接取这一层：被挡
      │   （同一主机、下一级的路径不受影响）
      ▼
[曲目页 HTML]  downloads.khinsider.com/album/<slug>/NN.mp3   → 200 OK  未被挑战
      ▼
[MP3 二进制]   lambda.vgmtreasurechest.com/.../NN.mp3        → 200 audio/mpeg  可用
```

"曲目发现层"被挡，而"曲目页层"和"音频层"没有。
这个形状也解释了用户的直接观感：**浏览器里能打开专辑页、能下载；程序直接请求专辑页被挡。**

## 4. 触发条件与影响因素

| 因素 | 是否影响 | 依据 |
|---|---|---|
| **网络出口 IP** | **是** | 校验由 Cloudflare 按出口下发；本次执行环境出口 `-HKG`（香港节点），2/2 被挑战。同一地址在别的出口可能不同 |
| 请求头 / User-Agent | **否** | 第 2 次用完整浏览器头，仍 403 + challenge |
| 请求频率 | 未观察到限流介入 | 返回的是 challenge，**不是** 429。两者在项目里被分成不同类别 |
| 时间 | 不确定 | 2 次探测间隔很短，都在同一时段，无法据此判断时段差异 |
| 请求路径 | **是** | 同一主机下，专辑页路径被挡、曲目页路径未被挡 |

需要强调一点：**"403"本身不等于"人机校验"。**
普通 403 也可能是路径不存在、地区限制等。项目里之所以能确定这是 Cloudflare 校验，
是因为**同时**拿到了 `cf-mitigated: challenge` 与校验页页面特征，而不是只看状态码。

---

## 5. 这个问题在项目里的表现形式

程序侧不是"报个 403 就完事"，而是把"被挡"拆成可区分的类别 —— 因为不同类别的成因不同：

| 程序内的异常 | 触发条件 | 含义 |
|---|---|---|
| `SiteBlockedError` | `cf-mitigated: challenge` 头，**或**页面含 `Just a moment...` / `challenges.cloudflare.com` | 真正的人机校验页 |
| `AccessDeniedError` | 403，但**没有**上面那些校验特征 | 普通"访问被拒绝" |
| `RateLimitError` | 429 | 被限流 |
| `NotAudioContentError` | 下载链接返回的内容不是音频（如 HTML 错误页 / 校验页） | 内容类型守卫 |
| `NetworkError` | 连不上、超时、传输中断 | 网络层失败 |

分类顺序是：**先判是不是校验页（不论状态码）→ 再判 429 → 其余 403 归"普通拒绝"。**

几个具体的实现点：

- `_looks_like_challenge(response)`：`cf-mitigated == "challenge"`，或页面头部含
  `<title>just a moment` / `challenges.cloudflare.com`。
- `classify_blocked_response(...)`：按上表顺序产出对应异常。
- `fetch_html()`：先判挑战，否则 `status_code != 200` 才抛通用错误 —— **不会仅凭 403 就标成 Cloudflare**。
- `download_file()`：即使下载阶段，也检查响应头里的 `cf-mitigated`，并配合内容类型守卫，
  避免把一个校验页当成 MP3 写进磁盘。
- 诊断输出脱敏：只保留白名单响应头（`content-type` / `content-length` / `server` /
  `cf-mitigated` / `cf-ray` / `cache-control` / `date` / `x-frame-options` /
  `content-encoding` / `vary`），`Cookie` / `Set-Cookie` / `Authorization` 一律剔除。

换句话说，**这个拦截问题在项目里被建模成"一类可识别的错误"，而不是一个笼统的失败。**

## 6. 范围与边界

**被挡的：**

- 程序直接请求**专辑页**（曲目发现层）—— 这是"输入专辑 URL 自动下载"这条路径的必经第一跳。

**没被挡的（实测 200）：**

- 同一主机下的**曲目详情页**路径（只测了 1 个曲目页，未逐一验证其余曲目）；
- **MP3 二进制子域**（`lambda.vgmtreasurechest.com`，`audio/mpeg`，4,930,262 字节，头 `ID3`）。

**与限流不是一回事：** 返回的是 `challenge` 而非 429，所以这是校验拦截，不是频率限制。

**与"站点无曲目"不是一回事：** 被挡时页面里根本不含 `table#songlist`，
它是校验页而不是"内容为空的专辑页"。把两者混为一谈正是 v008 要修的误报来源之一。

## 7. 尚未证实 / 未知的部分

下面这些**没有被证实**，不能当成结论用：

1. **浏览器与程序的出口是否完全等价。** 同机同网、`CF-RAY` 都带 `-HKG`，
   但浏览器会话可能带着已通过的 clearance cookie，程序没有。
   现有记录**不能**断言两者会话等价。
2. **曲目页的长期稳定性。** 只测了 1 个曲目页（200）。其余曲目未逐一验证，
   也不能保证将来不被挑战。
3. **专辑页的挑战是否随时间或出口变化。** 本轮 2/2 被挑战，但不排除其它时段、
   其它出口结果不同 —— 样本量太小。
4. **用户浏览器"等待很久"的性质。** 未采集浏览器侧数据，无法区分是交互式校验耗时，
   还是站点/网络本身慢。
5. **MP3 主机的长期稳定性。** 本次 200，属单次观察。

另有一条结构性限制值得单列：**曲目页与音频层当前未被挑战，是"当前观测到的状态"，
不是"保证"。** 如果这些层将来也被挑战，被挡的范围就不止专辑页这一层。

# 附：v1.0.0 修订（2026-10-15）—— 本问题已解决

> 上文 §0–§8 是 v007/v008 期的**现场记录**，保留原样作为排错史。
> 其中**已被后续实测推翻或需要修订**的地方列在下面。触发于用户指令：**帮我解决防火墙的问题**。

## 附.1 结论变化

| 上文的口径 | v1.0.0 的实测结论 |
| --- | --- |
| "是否放行取决于出口 IP 的信誉"（§0、§2） | **不是出口 IP**。是**客户端库的 TLS/HTTP2 指纹**：同一出口、同一秒，裸 `requests` → `403`，`curl_cffi`（`impersonate=chrome`）→ `200` |
| "程序不可解，只能靠导入浏览器保存的 HTML"（§0 结论、§5） | 程序**可以**自己过：传输层四级升级（指纹 → 浏览器 Cookie → 无头渲染 → 借本机 Chrome/Edge） |
| "请求头/UA 可能相关" | **完全无关**。补齐完整浏览器头仍 403；测试脚本把这一条留成了**反证组**，防止将来又绕回这个假设 |
| "曲目页与音频层未被挑战是当前观测状态，不是保证"（§7） | **这一点仍然成立**，保留。另外 §7 的 1–5 条未知项中，第 3 条("挑战是否随时间/出口变化")依然未证实 —— v1.0.0 只证明"指纹对不上就挑战、对得上就放行" |

## 附.3 边界（与上文 §6 一致，未放宽的部分）

- **没有**破解或代答校验题、**没有**接入打码接口、**没有**伪造 `cf_clearance`、
  **没有**复用他人的浏览器会话；
- L3 开全新临时浏览器会话，L4 用一次性临时配置目录（`--user-data-dir=<临时目录>`），
  **不读**用户浏览器的 profile / Cookie / 书签 / 历史；
- 仍然：顺序请求、低频、不并发轰炸（`REQUIREMENTS.md` Q7）。
- 性质说明：这是**用真浏览器一致的网络指纹去读任何人可访问的公开页面**，
  与"绕过登录/付费墙/限流"不是同一件事。
